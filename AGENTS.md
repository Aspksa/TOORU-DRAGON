# TOORU · DRAGON — инструкции для продолжения разработки

Перед изменениями прочитайте:
1. `ИСТОРИЯ/PROJECT.json` — принятые решения, реализованное, ограничения и план.
2. `ИСТОРИЯ/EVENTS.jsonl` — журнал обсуждения и изменений (один JSON-объект на строку).
3. `ИСТОРИЯ/README.md`, затем актуальные исходники и проверки в GitHub Actions.

История — контекст проекта, а не замена проверки кода. Сравните базовый коммит истории с текущим HEAD. Не выдавайте планы за работающие возможности. При противоречии фактическое поведение проверяйте по исходникам и тестам; новые указания пользователя имеют приоритет.

Обязательные договорённости:
- Русский интерфейс и корректный UTF-8, версия продукта пока `0.0.0`.
- Одно общее ядро. Сохранять утверждённое меню и порядок разделов.
- Основной запуск — `StartTooruDragon.bat`, с автоматическим открытием браузера после готовности сервера.
- Windows 10/11 x64, переносимый Python в `python/`; без системного Python, PowerShell и обязательного Git у пользователя.
- Пути вычислять от расположения проекта. Не привязывать к D:, имени пользователя или текущей рабочей папке.
- SQLite и личные файлы в `data/`; не коммитить базы, cookies, браузерный профиль, токены, логи, модели или резервные копии.
- Не заменять пользовательские данные при установке/обновлении. Изменения схемы — с миграцией и резервной копией.
- Автоматическое обучение Тори выполняется через Yandex AI Studio Responses API и Qwen3.6 35B. Старый браузерный Qwen-мост удалён; не возвращать автоматизацию chat.qwen.ai без отдельного пересмотра правил сервиса. Не считать накопление ответов изменением весов модели.
- Не добавлять зависимость от системного Python, PowerShell или обязательного `pip install openai`: основной путь к AI Studio реализуется стандартной библиотекой Python через HTTPS REST.
- API-ключ AI Studio является секретом: хранить только локально в `data/tooru.sqlite3`, не отдавать через обычный state API, не писать в Git, документацию, тестовые фикстуры или историю. Локальная БД пока не зашифрована — не утверждать обратное.
- Чат Тори использует контролируемый RAG: искать локально только по `memory`/`knowledge`, ограничивать число и общий объём фрагментов, не отправлять всю БД модели. Пользователь должен видеть список реально использованных записей и иметь возможность отключить контекст для отдельного сообщения.
- Локальный расчёт расходов AI строить только по фактическим usage-токенам ответа. Не выдавать его за официальный баланс Yandex Cloud. Тарифы и месячный лимит должны быть редактируемыми; при достижении лимита блокировать новые chat-запросы и ставить обучение на паузу.
- «Мозг Тори» работает через отдельный короткий reflection-запрос после чата. Он может только создавать pending-предложения в `brain_suggestions`. Память, Знания и очередь обучения изменяются только после явного `Принять`; `Отклонить` ничего не применяет. Токены reflection-запроса обязательно учитывать в AI-бюджете.
- Цели Тори хранятся в `brain_goals`. Планировщик может предлагать шаги `action` и `learning`, но не выполняет их сам. Учебный шаг попадает в очередь только после явного действия пользователя.
- После успешного ответа Qwen выполняется короткая самопроверка. Результат сохранять в `learning_queue.review_json`; обнаруженные пробелы превращать только в pending `learning`-предложения, без автоматического запуска.
- Для Qwen3.6 в Responses API текущий основной режим явно использует `reasoning.effort=none`: reasoning входит в `max_output_tokens`, увеличивает расход и ранее приводил к пустому финальному тексту. Менять это только после отдельной проверки стоимости и поведения на реальном API.
- «Разум Тори» хранит только структурированный, пользовательски проверяемый результат: факты, допущения, варианты, противоречия, решение, confidence и следующий шаг. Не сохранять и не показывать скрытую цепочку рассуждений модели. Для этого модуля также использовать обычный Responses API с `reasoning.effort=none` и отдельным JSON-форматом результата.
- Не добавлять сетевую доступность локального сервера без системы авторизации и явной задачи.

После значимого изменения обновляйте `ИСТОРИЯ/PROJECT.json` и добавляйте событие в `ИСТОРИЯ/EVENTS.jsonl`: что изменилось, что проверено, что осталось. Не переписывайте старые события. Указывайте фактические результаты; недоступные проверки отмечайте как непроведённые. Не помещайте личную переписку вне темы проекта в публичную историю.

Минимальная проверка кода: `python tests/test_core.py` (Windows: `python\python.exe -X utf8 tests\test_core.py`). Проверка истории: `python tests/test_history.py`. Расширяйте проверки только для изменяемого поведения.
